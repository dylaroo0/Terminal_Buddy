### 2. Technical Implementation (Phase B)

You already have the data. The `buddy-daemon` captures commands, filesystem deltas, and errors. We just need to add a **Summarizer Service**.

#### A. The Data Model (SQLite Update)
Your `SessionRecord` already has a `title` field. We need to add **tags** for grouping.

```rust
// shared/src/lib.rs
pub struct SessionRecord {
    pub id: Uuid,
    pub title: Option<String>,        // e.g., "Debugging API Auth"
    pub topic_tags: Vec<String>,      // e.g., ["docker", "backend", "bugfix"]
    pub started_at: DateTime<Utc>,
    pub ended_at: Option<DateTime<Utc>>,
    pub command_count: usize,
    pub auto_titled: bool,            // True if AI generated it, False if user edited
}
```

#### B. The Titling Engine (Inside Buddy Daemon)
When a session ends (or after 10 minutes of inactivity), the Daemon triggers a **Summarization Task**.

1.  **Gather Context:** Collect the last 20 commands, any errors, and files changed.
2.  **Prompt AI (Local or Cloud):**
    ```text
    User ran these commands: [docker-compose up, docker logs api, grep "error" logs]
    Files changed: [docker-compose.yml, .env]
    Errors seen: ["port 8080 already in use"]
    
    Task: Generate a short, human-readable subject title (max 5 words) 
    and 3 topic tags. 
    Example: Title: "Fixing Docker Port Conflict", Tags: ["docker", "networking", "debug"]
    ```
3.  **Update SQLite:** Save the title and tags to the session record.

**Cutting Edge Choice:** Use a **tiny local model** (e.g., `Llama-3-8B` quantized) for this. It doesn't need to be smart, just concise. This keeps it private and fast.

#### C. Configuration (`buddy.toml`)
Give the user control over how aggressive the titling is.

```toml
[behavior]
# How sessions get their names
session_titling = "auto"          # "auto" | "suggest" (ask user) | "manual"

# AI Model for titling (keep it lightweight)
titling_model = "local"           # "local" (privacy) | "cloud" (better quality)

# Grouping
auto_group_sessions = true        # Group sessions with similar tags together
```

## 🎯 Executive Summary

> **"A journal for your terminal that explains itself."**

Terminal Buddy is not a terminal emulator. It is a **second brain for your shell**—a persistent, searchable, explainable memory layer that turns every command into a learning moment and every session into a chapter of your technical story.

**The Wedge**: *"Show me what I ran last Tuesday."*  
Semantic, correlated history—commands + filesystem impact + system state—searchable in plain language. Nobody else does this.

## 🧭 Core Principles

| Principle | What It Means | Why It Matters |
|-----------|--------------|----------------|
| **Sessions are atomic** | Not commands—sessions (a focused block of work) are the unit of memory | Matches how humans think: "I was fixing Docker" not "I ran 17 commands" |
| **Journal, not buffer** | Notebook-style UI organized by date/topic, not a scrolling text log | Reduces cognitive load; makes history navigable for dyslexic/ADHD users |
| **Explainable by default** | One-click [Explain] turns any command into plain-language learning | Turns errors into teachable moments; builds confidence |
| **Accessibility-first, not accessibility-only** | Dyslexia-friendly defaults (OpenDyslexic, spacing, voice) framed as "designed for focus" | Ethical + strategic: wider market, stronger positioning |
| **Local-first, cloud-optional** | All core features work offline; AI/TTS can use user-provided API keys | Privacy as a feature; no vendor lock-in; sustainable cost model |
| **Daemon = brain, UI = skin** | MCP protocol separates intelligence layer from presentation | Future-proof: swap UIs without losing history; embed in IDEs later |

## 🧠 Intelligence Layer: Sessions, Titles, Topics

### Session Lifecycle
```
User opens terminal
        │
        ▼
Daemon starts session (UUID, timestamp, working_dir)
        │
        ▼
Commands executed → captured + correlated (filesystem + system)
        │
        ▼
Session ends (close tab / 15min idle / explicit end)
        │
        ▼
┌─────────────────────────────────┐
│ CLASSIFICATION HOOK (Daemon)    │
│                                 │
│ 1. Collect context:             │
│    • Commands run               │
│    • Directories visited        │
│    • Files changed              │
│    • Error patterns             │
│                                 │
│ 2. Generate title:              │
│    • Heuristic: working_dir +   │
│      most-modified files →      │
│      "Terminal Buddy Daemon"    │
│    • LLM (optional): natural    │
│      language title via user's  │
│      configured backend         │
│                                 │
│ 3. Assign topic tags:           │
│    • Fuzzy match to existing    │
│      topics OR create new       │
│    • Tags, not folders: session │
│      can belong to multiple     │
│                                 │
│ 4. Store in SQLite:             │
│    • title: "Fixing PTY timeout"│
│    • topic_tags: ["rust", "pty"]│
│    • auto_titled: true          │
└─────────────────────────────────┘
        │
        ▼
Session appears in Journal (Timeline + Topics views)
```

### Data Model Additions (SQLite)
```sql
-- Add to existing sessions table
ALTER TABLE sessions ADD COLUMN title TEXT;
ALTER TABLE sessions ADD COLUMN topic_tags TEXT; -- JSON array
ALTER TABLE sessions ADD COLUMN auto_titled BOOLEAN DEFAULT 1;

-- New table for user notes
CREATE TABLE session_notes (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    content TEXT NOT NULL,
    created_at TEXT NOT NULL,
    voice_clip_path TEXT, -- optional: path to local audio file
    FOREIGN KEY (session_id) REFERENCES sessions(id)
);
```

### Classification Strategy: Two Tiers
| Tier | Method | When Used | Pros | Cons |
|------|--------|-----------|------|------|
| **Heuristic (Default)** | Working directory + most-modified file paths + error keywords | Always, instant | Free, fast, private | Less nuanced titles |
| **LLM-Assisted (Optional)** | Pass command summary to user's configured LLM (local/cloud) for natural-language title | If user enables in `buddy.toml` | Richer, more human titles | Requires API key or local model; slight latency |

**Key**: Titles are suggestions. User can always rename/re-tag with one click. Buddy learns from overrides over time.

### Daemon Responsibilities (Rust)
- Session lifecycle management + classification hook
- Correlation engine (terminal + filesystem + system)
- Memvid writer (SQLite metadata + .mv2 binary frames)
- MCP server (stdio transport)
- Config parser (`buddy.toml`)
- **New**: Lightweight classification layer (heuristics + optional LLM call)

### UI Responsibilities (Tauri + React)
- Render Journal (Timeline + Topics views)
- Voice input bar (whisper.cpp integration)
- Command cards with [Explain]/[Note]/[Re-run] actions
- Focus mode + accessibility theming (CSS variables)
- Onboarding flow (interaction mode, font, TTS provider)
- **Dumb renderer**: All state management via MCP calls to daemon

### Plugin API: Deferred
- **Decision**: Do not build plugin system before installable alpha ships
- **Rationale**: Zero users → premature abstraction. Build three internal plugins first (theme switcher, voice pack, workflow template), then extract the boundary
- **North Star Interface** (for later):
  ```ts
  interface BuddyPlugin {
    name: string;
    component: React.ComponentType;
    triggers?: string[]; // e.g., ["onSessionEnd", "onError"]
  }
  ```

```typescript
// shared/config-schema.ts
export const BuddyConfigSchema = {
  appearance: { /* ... */ },
  interaction: { /* ... */ },
  components: { /* ... */ },
  // ...
};

```

### 2. React Component System (The "Building Blocks")
Each UI element is a self-contained React component with props:
```typescript
// buddy-panel/components/CommandCard.tsx
interface CommandCardProps {
  command: CommandRecord;
  explanation?: string;
  onExplain: () => void;
  onRerun: () => void;
  // ... accessibility props (aria-labels, focus management)
}
```
- Components register themselves with a **Component Registry**
- Creator Corner lets users enable/disable/reorder components
- Templates specify which components to load

### 3. CSS Variable Theme System (The "Visual Layer")
All styling uses CSS custom properties:
```css
/* themes/dyslexia-dark.css */
:root {
  --tb-bg-primary: #0a0a0a;
  --tb-text-primary: #f0f0f0;
  --tb-font-family: 'OpenDyslexic', monospace;
  --tb-line-height: 1.8;
  --tb-letter-spacing: 0.05em;
  /* ... 50+ variables for full control */
}
```
- Creator Corner has a live CSS variable editor with preview
- Themes are just CSS files + metadata JSON

### 4. Template Storage & Sync
- **Local**: `~/.terminal-buddy/templates/` directory
- **Cloud sync (optional)**: End-to-end encrypted sync via user's own storage (Dropbox, Nextcloud, etc.)—*no Terminal Buddy servers*
- **Community hub**: Static JSON index + CDN-hosted template files (read-only, no accounts needed)

### 5. Plugin API (Deferred but Designed For)

## 🎯 Creator Corner UX: Designed for Clarity

Since you're dyslexic and value simplicity, Creator Corner must **reduce cognitive load**, not add to it.

### Guiding Principles:
1. **Progressive disclosure**: Show only the most important options first. "Advanced" toggles reveal deeper controls.
